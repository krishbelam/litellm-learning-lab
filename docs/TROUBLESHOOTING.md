# Troubleshooting field notes

This file records the common issues encountered while building a local LiteLLM + Ollama + PostgreSQL lab.

## 1. Provider key vs LiteLLM virtual key

There are two different authentication hops:

- Application → LiteLLM Proxy: use a virtual key generated by LiteLLM.
- LiteLLM Proxy → OpenAI: use `OPENAI_API_KEY` if the selected upstream is OpenAI.

A virtual key cannot authenticate to OpenAI directly. With Ollama, no OpenAI provider key is needed.

## 2. Connection reset from the SDK

A Python `APIConnectionError` or `httpx.ReadError: [Errno 104] Connection reset by peer` is a symptom, not a diagnosis. Inspect:

```bash
docker compose ps
docker compose logs --tail=200 litellm
docker stats --no-stream
curl http://localhost:4000/health/liveliness
curl http://localhost:11434/api/tags
```

Check whether LiteLLM restarted, was killed for memory pressure, or failed to connect to its upstream.

## 3. `host.docker.internal` does not resolve on Linux

Linux Docker Engine may need an explicit host-gateway entry:

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

Then recreate the service:

```bash
docker compose up -d --force-recreate litellm
```

If that is unsuitable, use a reachable host IP in the model's `api_base`. Avoid assuming a Wi-Fi IP is permanent.

## 4. Ollama binds to loopback only

A host listener at `127.0.0.1:11434` is not normally reachable from a separate container. When Ollama is manually launched, stop it and run:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

If `systemctl edit ollama` reports that no such unit exists, do not create a new service blindly. First inspect how Ollama was launched:

```bash
ps -fp "$(pgrep -n ollama)"
systemctl list-units --type=service | grep -i ollama
systemctl --user list-units --type=service | grep -i ollama
```

For a desktop-managed or user-managed process, set the environment variable in the appropriate launcher/service configuration.

## 5. Missing tools inside a container

`getent: executable file not found` means that diagnostic binary is not installed in the image. It does not tell you whether DNS/networking works. Use a diagnostic image or Python where available.

## 6. Rate limits

A burst of concurrent requests is not sufficient by itself. Set an RPM/TPM limit on the virtual key or team in the LiteLLM UI/API. Use a dedicated test key and check the configured scope. A successful run may mean the limit was not configured, was set too high, or the requests did not exceed it during the active window.

## 7. Secrets and salt

Never commit real master keys, salts, provider keys, virtual keys, or database passwords. If a key is exposed, rotate/revoke it. Keep the LiteLLM salt stable after encrypted credentials have been stored; changing it can make existing encrypted values unreadable. Back up secrets securely before changing deployment configuration.
